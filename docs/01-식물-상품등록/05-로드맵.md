# 05. 로드맵 — PoC 이후 실사용까지

> 2026-10-29 작성. 현재 단계는 PoC. 클라이언트 인계 전 남은 작업을 정리함.

## 목표 모습

1. 클라이언트가 Codex 앱(PC·모바일)에서 사진과 상품명·상품정보를 입력
2. **중간 검토 — 미리보기**: 에이전트가 작성한 등록 정보를 근거와 함께 Codex 창에서 확인
3. 필요 시 대화로 수정 요청 → 미리보기 갱신
4. 승인 시 네이버에 **비공개 등록**
5. **최종 확인 — 판매자센터**: Codex 옆 창에 상품 수정 화면을 띄워 실제 등록 상태와 고객 화면(네이버 [미리보기]) 확인. 필요 시 직접 수정
6. "공개해줘" 시 판매 공개

## 1. 품질 기준 정립

결과 일관성을 확보하기 위해 항목별 작성 규칙을 명문화하고, 기준 세트로 검증함.

- 현재 기준은 `plant-agent/작성기준.md` 한 곳에 정리하고, 같은 판매자센터 형식의 **작성 기준 페이지**(작성기준.html)로 클라이언트에게 공개함 (2026-10-30)
- 클라이언트는 페이지에서 현재 기준을 확인하고 채팅으로 변경을 요청함. AI가 기준 파일·설정값을 고치고 변경 이력을 남김
- 아래 항목은 페이지에 `임시` 배지로 표시되며, 확정 시 배지를 제거함

| 항목 | 작업 |
|---|---|
| 상품명 | 네이버 공식 상품명 가이드 원문 확보. 클라이언트 기존 상품명 패턴 분석. 구성 규칙(요소·순서·길이) 확정 |
| 카테고리 | 쇼핑 검색 API 종료로 자동 집계 불가. **AI 선택 + 미리보기 검토(판단 근거에 네이버쇼핑 링크) + 판단 기록 축적** 방식으로 운영. 카테고리만의 별도 확인 절차는 두지 않음 (모든 항목을 미리보기에서 검토). 초기 판단 기록 확보 필요 |
| 태그 · SEO | 선정 기준(상품명과의 중복 여부, 연관 검색어 출처). 네이버 등록 불가 태그 목록 축적 (확인 사례: '관엽식물') |
| 상세페이지 | AI가 매번 HTML을 작성하는 방식에서 **고정 템플릿 + 내용 슬롯** 방식으로 전환. 디자인 일관성 확보 |
| 대표이미지 보정 | 표준 지시문 수립(배경 유형, 실물 형태·색·화분 유지, 과장 금지). 원본 대조 검수 단계 추가 |
| 가격 | 클라이언트 가격 사례 수집 후 규칙 확정 (컨설턴트 진행 중) |
| 평가 기준 | 클라이언트 기존 등록 상품 5~10개를 기준 세트로 구성. 규칙 변경 시마다 AI 결과와 비교 |

## 2. 2단계 검토 — 미리보기(등록 전) + 판매자센터(등록 후)

| 단계 | 화면 | 목적 |
|---|---|---|
| 중간 검토 | 미리보기 (로컬 HTML, Codex 창 내 표시) | 등록 전 결과물 검토. **항목별 값과 판단 근거**, 확인 필요 사항을 함께 표시 |
| 최종 확인 | 판매자센터 상품 수정 화면 (비공개 등록 후, Codex 옆 창) | 실제 네이버 등록 상태 확인. 고객 화면은 네이버 [미리보기]로 확인. 필요 시 직접 수정 |

Codex 앱 내 브라우저에서 판매자센터 상품 수정 화면이 열리는 것을 확인함 (2026-10-29). 고객 화면 확인은 네이버 [미리보기]가 가장 정확하므로, 자체 미리보기는 고객 화면 모방보다 **등록 정보와 근거 검토**에 집중함.

미리보기 개선:

| 항목 | 내용 |
|---|---|
| 구성 | 판매자센터 등록 화면과 같은 섹션 순서·명칭 |
| 근거 표시 | 항목마다 판단 근거 (카테고리 후보·수요, 상품명 키워드 선정 이유, 대표이미지 선택 이유, 가격 산출식) |
| 확인 필요 사항 | 상단에 모아서 표시 (임시 가격, 누락 정보, 검사 경고) |
| 원본 대조 | 대표이미지 보정본과 원본 사진을 나란히 표시 |
| 모바일 대응 | 휴대폰 화면 폭에서도 확인 가능하도록 반응형 구성 |
| 붙여넣기 지원 | 복사 버튼 유지 (클라이언트 계정 API 준비 전 대비책) |

등록 이후 단계에 필요한 기능:

| # | 기능 | 내용 |
|---|---|---|
| 1 | 수정 반영 (`update`) | 비공개 등록 후 대화로 받은 수정 요청을 등록된 상품에 반영 |
| 2 | 화면 수정 동기화 (`pull`) | 클라이언트가 판매자센터에서 직접 수정한 내용을 product.json으로 가져옴. 이후 대화 수정이 직접 수정분을 덮어쓰지 않도록 함 |
| 3 | 수정 화면 바로 열기 | 상품번호로 판매자센터 수정 페이지 직접 열기 (현재는 상품 조회 화면에서 검색 필요) |
| 4 | 미사용 초안 정리 | 검토 중 취소된 비공개 상품 삭제 |

## 3. 네이버 연동

| 순서 | 작업 | 상태 |
|---|---|---|
| 1 | 쇼핑인사이트 키 발급 (NAVER API HUB) | 완료 (컨설턴트 계정) |
| 2 | 커머스API 애플리케이션 신청 | 테스트 스토어 완료. **클라이언트 계정으로 재신청 필요** (자택 IP 등록) |
| 3 | 스토어 설정값 입력 (`config/store.local.toml`, 깃 제외) | 테스트 스토어 값 입력. 클라이언트 실제 값(주소록 ID, 배송비, A/S, 템플릿)으로 교체 필요 |
| 4 | 비공개 등록 시험 | 완료. 등록 불가 태그 1건 발견 후 규칙 반영 |
| 5 | 판매자센터 확인 | 완료. 공개 전환은 테스트 스토어에서 시험하지 않음 → 클라이언트 계정 첫 등록 시 컨설턴트 입회 하에 확인 |

## 4. 운영 환경

| 항목 | 작업 |
|---|---|
| Windows 설치 | Windows용 Codex 앱 제공 여부 확인, 설치, 승인 요청 설정 조정 |
| 모바일 사용 | 모바일 Codex의 실행 위치 확인(클라이언트 PC 실행 가능 여부 / 클라우드 실행 여부). 클라우드 실행 시 커머스API IP 제한 문제 발생 |
| 업데이트 배포 | 규칙·스크립트 수정을 클라이언트 PC에 반영하는 방법 수립. 현재 저장소는 퍼블릭이며 클라이언트 자료가 포함되어 있으므로 배포용 `plant-agent` 저장소 분리 검토 |
| 데이터 보관 | 상품 폴더 백업 방식 |

모바일 사용 선택지:

| 안 | 내용 | 비고 |
|---|---|---|
| A | 모바일은 사진·정보 입력과 확인만, 실행은 PC | 구조 변경 최소 |
| B | 클라우드 실행 + 고정 IP 경유 | 서버 운영 필요 |
| C | PC 원격 접속 | 클라이언트 사용 난이도 증가 |

결정 필요: 모바일에서 원하는 범위 (입력만 / 확인·승인까지)

## 5. 인계

- 클라이언트용 사용 안내 1장 (대화 예시: 등록 요청, 수정 요청, 등록 승인)
- 첫 3~5개 상품은 컨설턴트와 함께 진행
- 오류 발생 시 연락·전달 방식 정리
